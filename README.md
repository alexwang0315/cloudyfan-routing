# cloudyfami-portal

Cloudyfami 平台的平台轉送：把一個客戶端的訊息送給另一個客戶端，兩端各自連到平台，不必在同一個網路。依據 [ADR 0039](../docs/adr/0039-platform-relay-of-hca-summaries-to-granted-clients.md) 與 [ADR 0040](../docs/adr/0040-cloudyfami-platform-one-software-two-deployments.md)，整體規格見 [Cloudyfami 平台規格 v0.1](../docs/cloudyfami-portal-spec-v0.1-2026-11-27.md)。

目前完成 [#85](https://github.com/alexwang0315/cloudyfan-routing/issues/85)、[#86](https://github.com/alexwang0315/cloudyfan-routing/issues/86)、[#87](https://github.com/alexwang0315/cloudyfan-routing/issues/87)、[#88](https://github.com/alexwang0315/cloudyfan-routing/issues/88)、[#89](https://github.com/alexwang0315/cloudyfan-routing/issues/89)、[#93](https://github.com/alexwang0315/cloudyfan-routing/issues/93)：訊息信封、轉送服務、網際網路（HTTP）這一條鏈路、離線排隊與重新投遞、大檔分塊傳輸、客戶端程式庫與命令列工具、給 AI 代理用的 MCP 伺服器，以及 LoRa 鏈路（只在模擬中測過）。**只在本機驗證過**，還沒有部署，也還沒在兩台不同網路的設備上測過。第一階段不做授權檢查，客戶端以名稱自報身分，只適用於內部測試環境。

## 執行

只用 Python 標準函式庫，需要 Python 3.12 以上。測試借用 `../cloudyfan-mrc` 的環境裡的 pytest。

**照著做一次來回：** 見[使用說明](docs/usage.md)，用三個終端機視窗完成文字、回條、傳檔與查紀錄。

**讓 AI 代理接上：** 見 [MCP 伺服器說明](docs/mcp.md)。

在本機跑一次完整來回：

```bash
PYTHONPATH=src python3 -m cloudyfami_portal demo
```

啟動轉送服務：

```bash
PYTHONPATH=src python3 -m cloudyfami_portal serve --db /tmp/portal.sqlite3 --port 8790
```

執行測試：

```bash
../cloudyfan-mrc/.venv/bin/python -m pytest -q -p no:cacheprovider
```

## 結構

| 檔案 | 負責 |
|---|---|
| `envelope.py` | 訊息信封。完整形式是 JSON；精簡形式是一個不超過 200 位元組的封包，供 LoRa 使用。兩種形式可互相轉換，內容不變 |
| `relay.py` | 轉送服務：排隊、領取、回條、狀態查詢與傳送紀錄，存在 SQLite。它不知道訊息走哪條鏈路 |
| `transfer.py` | 大檔：檔案清單、平台端的分塊暫存、續傳、損壞偵測與空間上限 |
| `connectivity.py` | 斷線判定 |
| `http_link.py` | 網際網路這條鏈路：HTTP 轉接層，以及主動連出的客戶端 |
| `cli.py` | `cloudyfami-portal` 指令：`serve`、`demo`、`send`、`send-file`、`listen`、`status`、`log`、`clients`、`mcp` |
| `inbox.py` | 收到訊息後的處理：描述內容、把檔案存下來。命令列與 MCP 共用 |
| `mcp_server.py` | MCP 伺服器，走標準輸入輸出 |
| `lora_link.py` | LoRa 這條鏈路：分段、重組、只補傳缺的段、優先順序、拒送過大的內容 |
| `lora_sim.py` | 模擬的空中通道，會故意掉包、重複、亂序。不發射任何無線電 |

## 訊息信封

| 欄位 | 內容 |
|---|---|
| 訊息代號 | 16 位元組的隨機值。同一個代號重送只算一次 |
| 寄件與收件客戶端 | 名稱，1 到 32 位元組，不含控制字元與 `/` |
| 建立時間 | 整數秒。用整數是為了讓精簡形式不損失精度 |
| 類型 | 文字、短訊號、檔案 |
| 內容 | 位元組 |
| 大小與雜湊值 | 由內容算出。完整形式會附上並在接收時核對；精簡形式只帶雜湊值前 4 位元組 |

精簡形式的固定開銷是 28 位元組加上兩個名稱的長度。超過 200 位元組時明確拒絕，不截斷；分段屬於 LoRa 鏈路轉接層（#93）。

## 投遞狀態

```text
                    ┌─────┐ 逾時沒回條，重新投遞
                    ▼     │
已排隊 queued ──► 已送達 delivered ──► 已回條 acked
   │                  │
   └──► 已過期 expired / 失敗 failed ◄──┘
```

狀態只能往前。已回條、已過期、失敗是終點。「已送達」代表收件端領走了，「已回條」代表收件端確認收到。

| 規則 | 預設 | 指令參數 |
|---|---|---|
| 領走後多久沒回條就重新投遞 | 60 秒 | `--ack-timeout` |
| 最多投遞幾次，用完仍沒回條就標為失敗 | 5 次 | `--max-attempts` |
| 從排隊起保存多久，超過就標為已過期 | 7 天 | `--ttl` |

過期與失敗由服務自己判定，傳送紀錄的鏈路欄寫 `relay`。收件端不在線時，訊息一直排隊到過期為止，上線後依原本順序領取。

## 不重複的保證

- **寄件端：** 送出失敗時，客戶端用同一個訊息代號重試（預設間隔 0.5、1、2 秒）。平台對同一個代號只保留一份。
- **收件端：** 客戶端記得自己回條過的訊息代號。回條在路上遺失、平台重新投遞時，客戶端直接補回條，不把訊息再交給使用者。這份記錄放在記憶體裡，收件程式重開後會清空，所以重開後可能再看到一次尚未成功回條的訊息。
- **服務重啟：** 佇列與狀態都在 SQLite。實測以 `kill -9` 強制結束服務，重啟後 10 則訊息沒有遺失，也沒有重複交給使用者。

## 斷線判定

客戶端沿用 `scout-lora-qa` 的規則：連續 3 次連不上才算斷線，連續 2 次成功才算恢復，避免一次失敗就來回切換。`PortalClient.online` 回報目前判定。

## HTTP 介面

客戶端一律主動連出。

| 方法與路徑 | 作用 |
|---|---|
| `GET /health` | 健康檢查 |
| `POST /v1/messages` | 送出一則訊息 |
| `GET /v1/messages/{id}?until=acked&wait=秒` | 查一則訊息的狀態與歷程；可等到指定狀態 |
| `GET /v1/inbox/{客戶端}?wait=秒&limit=則數` | 領取排隊中的訊息，沒有訊息時可等待 |
| `POST /v1/inbox/{客戶端}/{id}/ack` | 回條 |
| `GET /v1/transmissions` | 傳送紀錄，含每個檔案傳輸的統計 |
| `GET /v1/clients` | 平台見過的客戶端與是否在線 |
| `POST /v1/transfers` | 登記一個檔案傳輸並預留暫存空間；再登記一次會回報還缺哪些塊 |
| `GET /v1/transfers/{id}` | 檔案傳輸的狀態、缺少的塊與統計 |
| `PUT /v1/transfers/{id}/chunks/{序號}` | 上傳一塊 |
| `GET /v1/transfers/{id}/chunks/{序號}` | 下載一塊 |

## 大檔傳輸

```text
寄件端                         平台                               收件端
  │ 登記檔案清單（大小、總雜湊、每塊雜湊）
  ├──────────────────────────► 預留暫存空間，不夠就拒收並記下原因
  │ 逐塊上傳，每塊核對雜湊值
  ├──────────────────────────► 收齊後核對總雜湊值
  │                            送出一則「檔案清單」訊息 ─────────► 收到清單
  │                                                    ◄───────── 逐塊下載，每塊核對
  │                                                               重組後核對總雜湊值
  │                            暫存空間釋放 ◄───────────────────── 回條
```

- **分塊：** 預設每塊 1 MiB，可設 64 KiB 到 8 MiB。
- **續傳：** 中斷後再呼叫一次上傳，客戶端只補傳平台回報缺少的塊。
- **傳輸途中損壞：** 收件端發現某塊雜湊值不符，重新下載那一塊，最多 3 次。
- **平台上損壞：** 平台在交出一塊之前重新核對。不符就把那塊標為缺少，回報收件端，寄件端再上傳一次即可。
- **空間上限：** 未完成的傳輸共用暫存空間，預設 2 GiB，由 `serve --spool-limit` 設定。超過時拒收，原因記在傳送紀錄。
- **釋放：** 收件端回條、訊息過期或失敗時刪除暫存；上傳一直沒完成的傳輸，超過保存時間也會過期並刪除。
- **檔案清單也是一般訊息**，類型為 `transfer`，所以回條、重新投遞與過期都和其他訊息相同。

實測一個 200 MB 的檔案在本機約 9 秒傳完，兩端雜湊值一致。這是同一台電腦上的數字，不代表跨網路的速度。

## LoRa 鏈路

**只在模擬中測過，沒有發射過任何無線電。** 實際發射受電信法規約束，每次都要使用者當次同意。

```text
資料框  0x01 | 標記 6 | 序號 1 | 總段數 1 | 一段精簡形式
狀態框  0x02 | 標記 6 | 總段數 1 | 已收到哪幾段的點陣
完成框  0x03 | 標記 6
```

每個框不超過 200 位元組。標記是訊息代號的前 6 位元組。

- **分段：** 訊息先編成精簡形式，每段最多 191 位元組。
- **只補缺的段：** 收件端湊齊就回完成框；段落停止進來時回狀態框，寄件端只補傳缺的段。寄件端等不到任何回應時整則重送。
- **次數上限：** 預設最多 5 輪，用完標為失敗，原因記在鏈路紀錄。
- **優先順序：** 短訊號先送，其次文字，最後小檔案。回應框永遠排在資料前面。
- **拒送：** 檔案傳輸一律拒送，因為它的塊放在網際網路上的平台；精簡形式超過上限（預設 1024 位元組）也拒送。兩者都記下原因，等網際網路恢復再送。
- **不保證順序：** 掉包時，後送的訊息可能先湊齊。鏈路不讓先湊齊的訊息等前面的，否則一則卡住會拖住後面所有訊息，包括求助短訊號。
- **不重複：** 收件端記得已完成的標記，重複的段只會讓它再回一次完成框。

在 30% 掉包、20% 重複、50% 機率亂序的模擬下，30 個隨機種子中至少 28 次送達；每一次不是完整送達一次，就是明確標為失敗。這是協定層面的檢查，不代表真實無線電的距離或可靠度。

## 新增一條鏈路

鏈路轉接層只需要呼叫 `Relay` 的 `submit`、`claim`、`ack`，並傳入自己的鏈路名稱。`tests/test_relay.py` 裡的 `FakeLink` 是最小範例，它用精簡形式收發，`relay.py` 不需要修改。
