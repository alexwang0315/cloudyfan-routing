# 基地部署與斷網切換

同一套程式有兩種角色（ADR 0040）。平時雲端負責基地之間的轉送；有民防需求、對外網路中斷時，每個基地改經 LoRa 互相轉送。**LoRa 的部分目前只在模擬中測過，沒有接上真正的無線電。**

## 每個客戶端都有一個家

| 家在哪裡 | 例子 | 這個客戶端連到哪裡 |
|---|---|---|
| 某個基地 | 家裡的 HCA、家人的手機 | 自家基地 |
| 雲端 | 跑在雲端主機上的外部代理 | 雲端 |

基地是住在那裡的客戶端的本地入口。寄給別處客戶端的訊息，基地依當下狀況選路：

```text
                 有網路                          斷網
甲基地 ── 推到雲端 ──► 雲端 ──► 丙基地拉走      甲基地 ── LoRa ──► 乙基地 ── LoRa ──► 丙基地
```

## 回條是端對端的

收件人回條後，收件人的基地發一則回條訊息，沿原路回到寄件人的基地。沿途持有這則訊息的基地也一併標為已回條。所以寄件人看到「已回條」，代表收件人本人確實收到，不只是下一站收到。

基地轉送後如果在逾時內沒等到回條，會再轉送一次，走當下可用的路。收件端記得自己收過的訊息，所以重複抵達不會讓收件人看到兩次；對已回條的重複訊息，它會再補發一次回條。

| 基地的預設 | 數值 |
|---|---|
| 等回條多久就重新轉送 | 120 秒 |
| 最多轉送幾次 | 50 次 |
| LoRa 最多經過幾個基地 | 3 |

## 斷網與恢復

- **判定：** 基地每次運作時探測雲端一次。連續 3 次失敗才算斷網，連續 2 次成功才算恢復。
- **斷網時：** 文字與短訊號改走 LoRa。檔案與超過 LoRa 上限的訊息留在基地排隊，不佔用無線電。
- **恢復時：** 還沒拿到回條的訊息，下一次重新轉送時改走網際網路；已經拿到回條的不會再送。斷網期間排隊的檔案也在這時送出，由對方基地先把整個檔案收進自己的暫存，再交給收件人。

## 跳數上限

每則訊息經 LoRa 出發時帶著「還能經過幾個基地」。每經過一個基地就少一，到了 1 還不是自己的客戶端，就不再轉送並記下原因。這避免訊息在網狀網路裡無限繞圈。

## 用設定檔啟動基地

```toml
name = "甲基地"
cloud = "https://雲端平台的網址"
tick_seconds = 1.0
max_hops = 3

[homes]
alice = "甲基地"
bob = "丙基地"
openclaw-agent = "cloud"
```

`[homes]` 沒列到的客戶端，視為家在雲端。

```bash
PYTHONPATH=src python3 -m cloudyfami_portal serve --role base --base-config base.toml --db /var/lib/cloudyfami/base.sqlite3
```

不加 `--role` 就是雲端角色。目前命令列啟動的基地**沒有 LoRa**，因為還沒有無線電驅動程式；它只會經雲端轉送。

## 驗證過什麼

全部在同一台電腦上，以模擬的 LoRa 通道與真的 HTTP 雲端進行：

- 三個基地排成一線、沒有網路，甲基地的訊息經乙基地轉到丙基地，回條沿原路回來。
- 有網路時只走雲端，空中沒有任何 LoRa 資料框；切斷雲端後改走 LoRa；恢復後收件人沒有收到重複，雲端也沒有那則訊息的副本。
- 沒有 LoRa 路徑可走的訊息，在網路恢復後經雲端送達一次。
- 斷網期間排隊的 3 MB 檔案，恢復後經雲端送到對方基地，雜湊值一致；寄件基地收到回條後釋放暫存。
- 四個基地排成一線、跳數上限 2，訊息在第三個基地停止轉送，最後寄件端標為失敗，無線電歸於安靜。
- 兩條路同時抵達的訊息只交付一次。
- 30% 掉包、重複與亂序下，3 則訊息與回條都完成。
- 網路時好時壞時，在線與斷網的判定不會來回切換。
- 以兩個獨立程序分別用雲端與基地角色啟動，基地上的客戶端與雲端上的客戶端互傳成功。

## 還不知道

- 真正的 Meshtastic 無線電、距離、空中時間與法規適用。
- 基地記錄「還能經過幾個基地」的資料在記憶體裡，基地重開會改用預設值。
- 斷網時基地沒有雲端的模型可用，能不能回答 AI 問題另行決定。
