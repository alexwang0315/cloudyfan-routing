# 容量與等待任務的重啟查核

這份文件描述 Issue38 的本機合成驗收範圍。真正供應商容量、帳單、吞吐量與正式服務 SLO 尚未核定；目前不表示已部署。

## 操作員可查核的事實

`GET /monitor/capacity` 與 `GET /monitor/queue` 只觀測保存的容量、窗口與等待任務。操作員可區分原本已知完成、尚未派送、已要求取消、送出後未決，以及目前無法核對的狀態。查詢不取得派送名額、不重送、不補抓供應商資料，也不會因窗口到期把健康狀態恢復。

`dispatch.integrity` 與 queue 的 `integrity` 採 `capacity-preservation-v1`。`status=unavailable` 表示目前不能以這份保存資料授權派送。若仍有獨立可信的舊資料，原 `observed_at`、期限、數量與費用不改寫，另外標出 `current_failure`。若沒有可信的完整舊資料，數量為 `null`，完整性旗標為 `false`；空陣列只是沒有可安全回傳的明細，不能解讀成零占用或額度可用。

可辨識的損壞保留原群組／任務見證並停止該範圍。另一個已登錄且原財務授權允許的群組，仍需通過自己的真實准入。無法辨識範圍、整份資料遺失、保存見證遺失或中斷交易尚未核對時，整份受控來源停止授權。

等待任務的原接受時間與期限不因程序 PID、租期、讀取或重啟重設。送出後未決的容量與原未知費用持續保留。取消尚未建立原始工作的接受紀錄，仍留下可讀的取消紀錄及終止圍籬，後續重送不得把它重新採用。30天原文存取依原到期時間判定；中繼至少保存365天，未知費用與未決派送繼續阻止清理。沒有自動刪除。

## 保存見證的實際界線

容量與 opt-in queue 各自保存私有的獨立見證，與原 TaskService／模型收據根目錄交叉綁定同一個儲存身分。見證保存完整的列成員與 SQL 選取欄位雜湊；queue 的原 `request` 只保存雜湊，不把提示文字複製到365天見證。原始模型 intent、response、費用帳本及健康紀錄仍由原本的儲存負責。

這是有固定上限的小型本機儲存實作：SQLite檔案最多64MiB、總中繼最多50,000列、交易日誌最多50,000筆。一般核對會雜湊整個有界資料庫；寫入會掃描有界中繼。它不是只查 hot index 或與歷史大小無關的常數成本。超出界線、待核對交易與不一致均停止授權，不自動清除舊紀錄、不重新替損壞資料認證，也不表示退款或可以重跑。這套機制不保證抵抗所有獨立見證一起被惡意回滾。

本版沒有通用自動修復或強制解除功能。供應商原費用、既有受控維護核對與刪除核准仍各自需要原證據；容量保存見證不能取代它們。

已完成任務的讀取沿用已登錄 Core／BackupCategoryCore 的原唯讀驗證器，每次仍核對原設定、結果與費用收據，不為觀察重建執行政策。未知自訂子類別保留原本依任務組裝的流程。這項讀取最佳化不快取授權、費用或結果，也不改變執行時的模型組裝、財務限制與送出前檢查。

操作員的容量、等待任務與完整頁面查詢，只在共同擷取等待任務與容量資料時短暫持有共享鎖，順序依序為等待任務、容量。核對原保存見證並完整複製有界資料後，先釋放原鎖，再讀取原費用與其他歷史。後續的等待任務與容量查核只讀不可寫入的副本；副本不能授予寫入、執行或派送權限，回應結束即關閉。下一次查詢與送出前准入仍重新核對原儲存；遺失、損壞與待核對交易不因舊投影恢復授權。

共同擷取點只涵蓋等待任務與容量；費用、任務檔案與其他歷史仍依原來源、各自的讀取時點查核，整份回應不保證來自同一時刻。較舊的觀測只組裝在這次回應，不回寫覆蓋後來完成的 Monitor 紀錄。若擷取到的仍是活動中的等待狀態，而稍後歷史已完成，這次投影將完成、通過與路徑保留為未知，標示 `metadata_changed_during_read`，不把較新的完成結論混入較舊的等待資料。

在已設定受控排隊協定的服務中，主機唯讀觀測即使沒有在舊佇列副本看到新任務，仍核對原身分、原存取期限與保留政策，並檢查時鐘有效且沒有倒退。這條觀測路徑不占用用來建立／執行任務的保留鎖，不補建接受或保留紀錄，也不推進保留時鐘。新任務原資料尚未齊、已過期或目前無法核對時，明示待核對／不可用，不能猜成已派送或完成。建立、執行與其他入口仍沿原授權及保留規則；未設定此受控排隊協定的觀測路徑保留原鎖定行為。

## 操作員登入與資料待讀取

重新登入先以 `GET /monitor/session` 核對原 Host、Origin 與操作員 Bearer。只有收到這次核對的 HTTP200、正確固定版本與身分核對成功標示，且目前登入版本仍相符，才完成登入，再背景讀取完整資料。這個小型唯讀介面不建立新 token，也不讀任務、容量、健康或帳務。完整資料未到時明示讀取中，不以空清單或零值代替；等待任務與容量頁可透過各自原有授權端點讀取，無須先等整份歷史。

每次換身分都清除先前可見資料，並以新的登入版本隔離舊請求。晚到的成功回應、401 或控制操作結果，不能恢復或清除較新的登入、覆蓋新資料或關閉較新的確認視窗。已知的安全拒絕先呈現，相關歷史再背景更新；這不延長授權或期限，也不新增模型、來源或核帳請求。

## 本機驗收入口

`tests/capacity_resilience_fixture.py` 提供 `build_resilience_host` 與 `build_resilience_health_host`。後者組合真實 BackupCategoryCore、HealthStore、TaskService、IdentityStore、BudgetStore、CapacityStore、CapacityWindows 與 QueueScheduler；所有模型／來源／核帳上游皆使用 MockTransport。程序間共用原儲存與持久化憑證，代際 ID 每次啟動皆唯一。

完整桌機合成跑次的 Mock 上游完成訊號等待上限，預先設定為3600秒。這只是讓驗收程序有明確的有限等待，不延長任務原接受期限、容量窗口或原文存取期限，也不是產品回應時間或正式服務 SLO 承諾，不能據此認定真實供應商容量或吞吐量。

故障驗收先完成同一實際路徑的正常重開控制，再把原資料庫移入保留區，於同一路徑建立新的選擇性複本或更改複本的 SQL 索引欄位。原件、雜湊、失敗、逾時、HTTP／網路及原費用收據全部保留，不以刪表或刪檔製造測試。
