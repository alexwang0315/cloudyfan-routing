# CloudyFan Monitor 第一版本機接入方案

日期：2026-10-22（Asia/Taipei）。狀態：使用者已確認Q1～Q12及整體方案，並明確授權開始本機接入與驗收；目前實作進行中，驗收結果另見[執行檢查點](execution-checkpoint.md)。

## 目標與完成範圍

2026-10-22 最新指示：停止手機端介面的製作與測試；本次畫面驗收限於桌機，原手機驗收要求由此調整。

將既有Monitor接到受控TaskService，讓單一操作員透過管理介面查看運作狀態、完整帳務、23類候選池及個別客戶端統計，並設定四種路由模式。沿用現有Core／BudgetedCore及驗收、費用資格機制，不另實作路由演算法。

第一版的實際任務入口為同步 `/v1/tasks`，本機驗收使用兩個獨立客戶端。四模式維持：CloudyFan MRC（`cloudyfan`）、全大模型優先（`fixed_high`）、全便宜模型優先（`low_first`）及全開源模型優先（`open_source_first`）；各模式嘗試與升級行為由已註冊的既有核心契約決定。

本方案的完成指本機受控接入、模擬上游的端到端驗收及一次限定來源GET查核。它不代表真實模型或費用資格已成立、正式服務已部署，或真實降本率已驗證。

## 十二項已確認決定

| 決定 | 第一版行為 |
| --- | --- |
| Q1：客戶端單位 | 一個client是一個可獨立授權、設定模式與查看統計的應用或服務身分。同一客戶可有多個client；換憑證保留原身分、任務與統計。 |
| Q2：接入入口 | 採同步TaskService `/v1/tasks`，以兩client完成本機接入；Queue及OpenAI／Ollama相容入口不列為此次首版接入完成條件。 |
| Q3：管理權限 | 單一CloudyFan操作員管理全域、各client模式與模型池；client僅能建立／接續自己的任務並查看自己的結果與統計。 |
| Q4：帳務與預算 | 各client分列費用及使用量，付款帳戶共用原總預算；第一版不新增每client美元額度。同帳戶未知費用仍停止相關client新派送。 |
| Q5：任務存取 | 建立後30天內可查看結果及依原條件接續；到期明確顯示「已到期」，拒絕結果讀取與接續，重送／重啟不延長期限。 |
| Q6：資料保存 | 原始請求及答案滿30天後列入清理審查；帳務、操作紀錄、歷史統計及使用過的版本證據至少保存365天。未知費或有效任務引用延保，實際刪除逐項批准。 |
| Q7：候選與契約 | 保留23類高／中／低／開源四欄候選池視圖，開源欄可與品質欄重疊；另列類別×四模式的契約註冊狀態。缺合法契約則標原因並拒派，已註冊仍須通過原資格與預算檢查。 |
| Q8：容量 | 全服務同時最多執行一件模型任務；另一件新任務滿載立即429，不暗中排隊；查詢及監控仍可回應。 |
| Q9：重送與接續 | 同client／run及相同內容重送，只回原狀態或結果，不觸發新模型請求；確定中斷的任務只有顯式resume可依原條件接續。 |
| Q10：來源更新時機 | 操作員手動更新來源，先看差異再發布候選；執行模型池啟用維持獨立操作，記錄來源、更新時間及完整度。 |
| Q11：來源部分失敗 | 主要來源與schema成功時，個別端點故障／逾時／未查可形成可發布的部分候選，須明示完整度與未知欄位。主要來源失敗維持舊版。發布不授予執行資格。 |
| Q12：客戶端斷線 | 伺服器正常時已接受任務繼續執行，以原client／run查詢；斷線不代表取消或無費用。服務程序真的中斷後不自動接續，依Q9及原帳務限制處理。 |

## 任務與管理流程

1. 由主服務識別client與操作員，統一既有身分及憑證生命週期；換憑證後維持原client，已撤銷憑證不能繼續存取。管理憑證不出現在前端程式或證據中。
2. 新任務固定client、run、內容指紋、類別、模型池版本、模式與契約；client模式覆寫優先於全域預設，模式及模型池變更只影響未來任務。未經此入口的舊任務不自動接管。
3. 同client／run的重送先辨識原任務，不佔用新的執行名額，也不再呼叫模型；改內容拒絕。到期、退休或缺少原契約的任務不被另建、默默遷移或復活。
4. 只有真正的新任務或明示接續會申請執行名額，並繼續經過既有資格、費用上界、預算及未知費檢查。同一本機服務的程序／worker共用一件執行容量，不能每個worker各放一件。滿載的新任務拒絕後，不會在之後自行啟動。
5. 任務執行時，狀態查詢、監控及管理操作仍能回應；客戶端連線斷開不提早釋出執行名額。程序真正中斷時，依持久狀態及原帳務證據處理，不憑重啟後記憶體清空就認定可重新派送。
6. 操作員只可啟用主服務已註冊且符合原資格的確切pool／category／mode／contract組合；既有任務保留舊契約，後續部署／重啟也須保留仍需使用的版本。

## 帳務與保存口徑

- 付款帳戶須使用包含原有歷史的共用完整帳本；不能另建檔案或服務實例來繞過未知費停止。各client只呈現能由證據歸屬的任務費用，帳戶的歷史／未歸屬支出另列，未知費維持未知。
- 30天是客戶端存取有效期，也是原始內容可進入清理審查的門檻，不是自動刪除時間。內容與結果到期不把既有費用、通過紀錄或歷史統計歸零，也不顯示為一般工程中斷。
- 帳務、操作紀錄、歷史統計與使用過的版本證據至少365天；未完成核帳或仍被有效任務引用時延保。一般紀錄自建立時點起算，共用模型池／契約版本證據自最後一次任務使用起算，避免舊版本剛被新任務使用就列入清理；單純查詢或重送不重設期限。此為整體確認時一併檢視的落地口徑。
- 清理只先產生精確preview，列出目標、大小、風險與開啟狀態，待逐項批准才刪除。保留原核帳、引用及防重送／退休標記的保護，不因內容到期而移除保護。

## 來源更新流程

1. 操作員手動觸發一次有界GET更新；固定主要模型與評測來源，最多額外查12個模型端點，失敗也計入最多15次嘗試。單次最長15秒、整輪最長60秒，不跟redirect，不讀取模型作答或分類端點。
2. 主要來源或其必要schema失敗，整輪失敗並保留舊候選版本。主要來源成功但個別端點HTTP／網路／解析失敗、逾時或未查，保留已取得資料，標成部分更新；列明成功、失敗、未查數目及原因，缺資料不猜值。
3. 操作員查看差異後才發布候選；發布與執行模型池啟用分開。開源候選欄只是候選集合，不由此推定授權、免費、本地可部署或實際執行資格。
4. 來源GET驗收另在明確記錄的測試窗口執行一次，與模擬模型驗收分開；該次不自動發布或啟用，保留URL、時間、schema查核與不含憑證的呼叫證據。

## 完成條件

依[完整驗收清單](main-thread-integration-acceptance.md)全部取得適用證據：

- 兩client隔離、憑證輪替、四模式、23類候選及契約矩陣、模式切換後原任務重連。
- 真實本機HTTP下的一件容量、跨worker／程序仍共用該容量、滿載429、長任務監控、重送不再派送、斷線後原任務繼續及程序中斷後明示接續。
- 30天到期邊界、重啟不延長、歷史統計保留、365天證據與延保／清理preview。
- 共用帳戶未知費阻擋其他client，總帳保留歷史與未歸屬費用。
- 來源故障及部分更新、桌機實際操作，以及一次真實來源GET成功與schema查核。

模型工作驗收使用真實Core／TaskService搭配模擬上游、虛構憑證及合成費用；只開放該測試的loopback HTTP，其餘模型網路受阻。實際來源GET另作獨立步驟，兩者均須以呼叫紀錄與網路限制佐證，不以寫死的零呼叫欄位替代。

受影響檢查、本機HTTP、瀏覽器或來源GET任一項未通過／未執行，就明列缺項，不能把文件或舊35項回歸稱為本次主線接入完成。
