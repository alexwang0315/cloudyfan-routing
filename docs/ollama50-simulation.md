# 一個 Ollama 客戶的50題 MRC 模擬

本案例驗收一條完整呼叫鏈：官方 Ollama Python SDK → 真正 loopback HTTP → Ollama相容入口 → Monitor Gateway → TaskService／BudgetedCore／Core → 合成模型與 Jev 回應 → 公開驗收 → Monitor任務及客戶帳本。模型與費用皆明示合成，不讀取真實憑證，也不呼叫供應商；原主線付費研究、答案與歷史未知費不載入此案例。

## 客戶問什麼、如何驗收

固定50題不同的整數加法。客戶只送公開問題、路由別名、非串流選項及穩定run ID；不傳標準答案、期望模型池或預先決定的成功狀態。驗收器從已凍結的公開問題獨立計算答案；合成傳輸依下列透明腳本回覆，真正核心負責首次作答、驗收、每階段 Jev 二選一及補答。

| 題號 | 預設合成路徑 | 最終公開驗收 |
| --- | --- | --- |
| 01–10 | 開源 | 通過 |
| 11–20 | 開源 → 低池 | 通過 |
| 21–30 | 開源 → 中池 | 通過 |
| 31–40 | 開源 → 中池 → 高池 | 通過 |
| 41–45 | 開源 → 低池 → 高池 | 未通過 |
| 46–50 | 開源 → 中池 → 高池 | 無法確認 |

其中一題的第一次 Jev 回傳同分，核心須保守選中池，Monitor應顯示原回報與實際選池差別。選項分布是路由資料，不是任務答對機率。全組應產生40通過、5失敗、5無法確認，110次模型作答與60次Jev，共170筆合成用量；此為腳本覆蓋範圍，不能當成真實模型能力或降本實驗結果。

## 機房端應看到什麼

- 總覽的50題面板：客戶、Ollama別名、本批次進度、明示啟動及重新執行按鈕；一般頁面輪詢只讀取，不發送題目。
- 客戶端：單一受信任身分的50件任務、模式、最近活動、首答與最終成功／失敗／無法確認。
- 任務與升級：每題凍結的模式與模型池、Ollama入口、各次作答模型／供應商／token／費用，四池實際執行狀態及未選狀態。
- Jev明細：開源失敗或無法驗收後的低／中二選一、最近一次補答後的中／高二選一、觸發原因、回報選項、真正選池、保守fallback及分類費用。提示詞、答案原文與原始回應不帶入Monitor。
- 費用帳本：分類與生成各筆費用，包含失敗及公開驗收未知的已知用量；公開驗收未知不等於費用未知。
- 客戶帳務：供應商合成成本與客戶用量費分列，開源成本0仍有可調售價；重送與重複核帳不新增模型派送或重複扣款。

## 合成價格

每次作答20輸入／1輸出 token；開源模型供應商費0、低池0.0003、中池0.001、高池0.004 USD。每次Jev為10輸入／1輸出、0.0001 USD。客戶倍率1.2，開源服務另用輸入0.4／輸出0.8 USD每百萬token，初始入帳1 USD。

以上路徑的獨立手算預期為：供應商成本0.1155 USD、客戶扣款0.139128 USD、內部餘額0.860872 USD。真實模型API費用為0。費率在任務建立時固定，帳務保持可重試與可查核；整批核帳沿用每批20項上限，直到本次合成用量處理完，不能放寬核心預算或未知費停止。

## 原生介面範圍

沿用 `cloudyfan-ollama-text-v2`：`GET /api/tags`、`POST /api/chat`、`POST /api/generate`，單一user文字、`stream:false`、Bearer客戶憑證與`X-CloudyFan-Run-ID`。SDK固定0.6.3；它會忽略CloudyFan擴充欄位，完整結果及費用透過同一run的`/v1/tasks/<id>/result`及Monitor API核對。

服務端別名固定到精確註冊的MRC契約。若操作員先切換到另一個模式／模型池，原生請求在派送前回409，不能在另一契約下假裝同一別名已執行；已接受的任務及相同內容重送維持原凍結契約。串流、多輪對話、圖片與任意工具不在這個相容子集，未開放一般Ollama CLI的完整指令集。

## 啟動與操作

在 Monitor 專案目錄執行 `./scripts/preview --simulation50 --port 18773 --data runtime/ollama50-example/data`，再開啟 `http://127.0.0.1:18773/`。資料目錄須全新或已具有相同模擬識別；伺服器日誌應放在資料目錄之外。此旗標不能與真實 OpenRouter 帳務憑證或舊示範旗標併用，啟動及讀取頁面不會自動送題。獨立重建環境須安裝 Monitor 的 `simulation` extra；目前開發環境已有固定版本的官方 SDK。

1. 總覽按「執行50題模擬」，確認後可觀察進度。服務端以只具客戶權限的SDK送題，不把操作員權限交給客戶。
2. 「查看此客戶端任務」自動篩選客戶；搜尋 `q31` 並展開「查看呼叫與選池」，可查看同分保守選池與第二次升級。`q01`、`q11`、`q21`、`q41`、`q46` 分別展示其他路徑及結果。
3. 「費用帳本」看供應商合成用量；「客戶帳務」看倍率、開源token售價、儲值與逐筆扣款。批次完成會按既有20筆上限分批核帳，一般頁面讀取不會扣款。
4. 再次執行會建立新批次，追加50件任務與對應合成帳務；既有批次及失敗證據保留。同批次的相同run內容重送只讀原結果，工程失敗不自動重試。

## 執行紀錄

本輪先確認本機服務與桌機中間進度，首個真HTTP批次在第23題收到401，僅完成22題，不能列為50題通過。原始資料位於 `runtime/ollama50-20261023-live/data/`，瀏覽器失敗證據位於 `output/playwright/ollama50-20261023/`，保留排查。已排除憑證過期、撤銷、停用與不存在的驗證次數限制；原例外沒有被舊入口記錄，確切原因仍未知。

檢查另發現身分資料庫伴隨檔可能在存在檢查後被正常SQLite提交移除，且密集並行短交易實測出現1次工程例外。修正採單次檔案檢查與同一registry的短交易串行，1,800次並行活動檢查零故障；不安全伴隨檔、時鐘回退、撤銷與scope仍拒絕。憑證本身無效回401；驗證器或後續principal檢查的工程故障回安全503並停止，不作HTTP重試。
