# 品質、成本與速度共同決定候選及分類是否值得

2026-10-20；使用者要求的選模規則修正。本文前段保留最初設計與差距，後續已依授權新增明示選用的離線實作；詳見[實作契約與限制](qcs-offline-implementation.md)。RG-01、SQL判分、原有快照／路由預設與付費結果保持原版。本輪沒有模型／帳戶API、全大模型獨立對照、部署或推送。

## 明確目標與設計時的實作差距

目標仍是整批題目全部答對，在事先固定的可接受速度下，讓完整成本最低。高／中／低榜分只是能力層級，不代表每層都值得付費分類。品質不合格不能因便宜或快而入選；沒有速度承諾時也必須保留可觀測速度資料及未知狀態，不能默認為最快。

| 現有程式 | 實際行為 | 必須補的部分 |
|---|---|---|
| scores/adapters.py:parse_openrouter_benchmarks | 只讀AA intelligence／coding／agentic指數；未保留pricing，不支援Design Arena資料型態 | 分開保存品質、成本及來源有提供的速度證據，不宣稱每個來源都有三維 |
| scores/catalog.py:select_profiles | 按能力／context／provider過濾；群內依選填estimated_request_usd、再estimated_latency_ms排序 | 任務層級完整成本與延遲限制、資料時效／精確設定綁定、跨池比較 |
| routing.py:build_request | 公開能力卡及外部分數進入Jev；沒有明確三維契約及付費分類回本檢查 | 投影適用的三維摘要與來源；在付費分類之前判斷其經濟價值 |
| 現有四候選 | 低／中普通token單價相同；完整任務成本與速度尚無合格估計 | 不視為已具合理成本階梯；先重選或以新版本略過無淨節省的階段 |

這張表描述開工前的缺口。後續新程式不改原 adapter／CLI 的歷史語義，而是新增 metrics 正規化與 QCS opt-in 接入；不能用原有1,322項紀錄驗證新程式。

## 三個維度如何取得及保存

[官方OpenRouter參考](https://github.com/OpenRouterTeam/skills/blob/main/skills/openrouter-benchmarks/references/benchmarks-api.md)不是固定三個同名欄位：AA型態提供任務指數及pricing；Design Arena型態另有平均生成時間。速度可另外參考指定provider的endpoint觀測；benchmark模型身分與可呼叫版本仍需對照。本輪只查官方schema原文，沒有用金鑰讀benchmark資料。

| 維度 | CloudyFan的定義 | 資料契約與限制 |
|---|---|---|
| quality | 任務適用的能力先驗＋獨立資格 | 保留來源、版本、metric、尺度、強度與時間；SQL是否能用仍依獨立SQL資格，不能將分數轉成答對率 |
| value／cost | 成本，不是效益分數 | 保存USD/token、USD/request、cache及其他費率；再按任務token／修正／升級估計流程成本。來源若提供比值或排名，保留原指標，不能冒充USD費用 |
| speed | 指定模型設定／provider的耗時表現 | 分開記TTFT、tokens/s、每次請求延遲、含分類／補答的完整流程耗時；保留統計量、樣本、期間、負載及冷／暖狀態。平均值不當p95，吞吐不當整件延遲 |

每個維度各自有source URL／hash、取得時間、觀測期間及效期，綁定模型版本、強度、provider、服務tier／量化與工作量；家族榜分與精確API實測分開。不得把別的provider的最低價格和最快速度拼成不存在的候選。成本／速度缺失、過期或只有不適用的工作量，不能填零、刷新日期或視為已完成三維資格。

OpenRouter、AA、LiveBench或CodexRadar可提供各自維度的一部分；不要求接完所有來源，也不跨來源平均品質分數。先補來源正規化，明確列出哪一維缺資料；benchmark或一般價目表不能替代RG-04的費用保障。

## 新版選模的固定順序

1. **品質及執行限制先過濾。** 任務操作、context、固定版本／強度、provider與獨立資格都要符合；保持榜單高／中／低的原生分群。未知不能當低分或合格。
2. **檢查速度與來源時效。** 事先固定任務的最大流程延遲及測量口徑；有硬限制且缺相應證據時不能宣稱符合。TTFT或tokens/s只作各自口徑的參考。
3. **計算每條可達路徑的完整成本。** 包含分類、生成、reasoning、cache、失敗、修正、升級及下一個分類器。若估算host／驗收／人工成本，單價未知另列，不填免費。預期值、信賴區間、實付與可強制上界分開。
4. **排除沒有競爭價值的候選。** 在同一任務與可比證據下，若候選沒有品質／速度優勢，完整成本亦不較低，則不用它製造二選一。不得僅以較低榜分斷定任務能力較差，或以同token單價斷定總成本相同。
5. **檢查跨池價差與分類回本。** 比較「直接用適當合格候選」與「先付Jev再選擇」的完整後續路徑。只有扣除分類、失敗及升級成本，且保守估計仍超過事先固定的安全餘量，才付分類費；否則直接選模。不能為保留三層架構強迫支付裁判費。
6. **有值得比較的二候選才交給Jev。** 先投影三維摘要、適用限制及公開失敗診斷，再由Jev判斷任務所需能力。第二次選擇仍用最新失敗設定／答案／公開診斷；隱藏答案、隱藏判分及其他組答案不參與。新流程需新routing／manifest版本，不能改舊任務續跑。

概念計算為：

```text
分類淨節省 = 直接使用適當合格候選的預期完整成本
             - [Jev費 + 各選擇結果機率 × 該結果之後的完整路徑成本之加總]
```

後續路徑成本包含所有可達補答／升級，不能只放第一次生成費。選擇與失敗風險須來自獨立校準／適用歷史資料，含不確定性；不能用正式題答案或Jev自報信心當成真實機率。沒有證據時不主張最佳化，採事前明定且符合資格的直接路徑或回報不足；若沒有合格直接候選，拒絕／保留未知，不假稱送中階必定答對。

不預設低／中必須差30%或某個固定倍率：必要價差隨任務token量、分類費、升級風險及速度限制變動。具體數值與安全餘量在獨立校準後、正式題前凍結。原80／100的品質邊界不等於成本門檻，也不再使用全域平均成本替所有任務作決定。

## 實作與離線驗收順序

1. **資料層**：補benchmark pricing／可用speed及provider觀測的正規化、單位、缺值、時效與身分綁定；不丟原資料，不從缺欄位推定免費或無限快。
2. **候選準備**：新增明示版本的三維政策、速度約束、成本工作量及跨池有效價差，輸出可讀的排除／直接選模原因；舊快照與CLI行為保持歷史語義。
3. **付費前決策**：補分類淨節省門檻、direct／classify／insufficient等可觀測結果與公開投影，讓不值得裁判的情況真的零Jev請求。保持嘗試上限、完整預留及unknown stop。
4. **離線反例**：同完整成本且中階能力充分→直送中階；只有不同單價但完整成本更高→不選；低階便宜卻升級風險吃光節省→直送；Jev費大於可省差額→零分類；速度限制不符→排除；來源缺值／過期→不假裝合格；資料拼接錯provider→拒絕；淨節省可靠且品質／速度符合→才分類。另驗證原任務不換政策、不重送、第二選擇器使用最新公開診斷。
5. **真實試驗規劃**：上述離線通過後才重新挑選候選、校準估計並凍結新計畫；正式模型資格／路由比較的題目不可反過來挑規則。原US$60與四候選是前版提案，不在目前組合上直接啟動。全大模型獨立對照仍停用。

## 後續離線實作與尚未驗證

新增 `scores.metrics`、`scores.qcs`、`ScoreCore(qcs_plan=...)` 與完整預算接入，實作三維資料保存、逐候選篩選、完整成本比較及零 Jev 直接路徑。新政策 `hierarchical-qcs-v1` 與原預設 `hierarchical-sequential-v1` 分開，不套回舊凍結任務。

直接比較基準必須是合適的較低成本候選，不能拿昂貴 `direct_tier` 放大分類節省。同一份成本預測下不應付分類費；若主張分類能減少低模型試錯，須另有同母體、固定分類器及 payload 契約的條件成本校準。速度除了各階段，另需整件含開源首答與驗收的同統計量預測；不加總 p95。

最新離線測試與證據見[實作說明](qcs-offline-implementation.md)。真實候選的獨立 SQL 能力、來源使用範圍、任務成本／耗時／條件機率校準及供應商費用保障仍未取得，正式資格維持待核定。原四候選／US$60計畫仍不啟動，沒有新增真實降本率或延遲承諾。
