## 先看結論

🟢 **路由、模型池、費用控管與接入功能已有實作，也留下了離線測試紀錄。** 「待核定」不代表這些程式全部還沒寫。

🟡 **正式服務還缺實際使用條件下的證據。** 例如：API 回傳的是否真是指定模型、該模型是否能完成指定 SQL 任務、供應商收費是否真的有可強制的上限。目前十項正式放行記錄都仍是 `pending`（待核定）。

🔴 **現在優先處理模型能不能用、評分能不能持續更新，以及費用能不能控制（RG-02／RG-03／RG-04）。** SQL 驗收器（RG-01）保持凍結，只在相關變更時做必要回歸，不再重審 S01～S08，也不因「待核定」就反覆重跑同一批實驗。

先做哪幾件、哪些可以不花模型費完成，見[SQL主備模型包落地清單](sql-backup-pool-readiness-plan-20261021.md)。這是待辦與前置條件，不是新包已合格或新的付費授權。

較早整合版的完整離線紀錄為 **1,322 項測試**，另含 Ruff、兩個模擬示範及套件建置；見[最新資格執行器整合證據](evidence/sql-runner-offline-20261020.json)。先前順序式路由的[1,304項紀錄](evidence/sequential-integration-offline-20261020.json)保留為歷史證據。`project-state` 為 `offline_verified`，正式資格仍待核定。先前模型資格 v2 的[1,281項紀錄](evidence/sql-model-offline-20261020.json)保留為歷史證據；後續程式變更須重新核對來源指紋，不能沿用舊結果。

## 現在的路由流程

依[順序式路由規則](sequential-routing.md)：

1. 先由開源模型回答，再依公開的任務要求檢查答案。
2. 通過就結束；未通過或無法判定時，Jev 在低分、中分模型中選一個，讓它回答並再次檢查。
3. 仍未通過或無法判定時，Jev 再從中分、高分模型選一個，作最後一次回答與檢查。
4. 最多作答 **3 次、選模 2 次**。最後仍不合格或無法判定，就保留該結果，不能記成成功。其他對照模式仍最多作答 2 次。

第二次選模使用第二次作答的模型設定、答案與公開診斷，不重用開源首答的舊診斷。中／高選擇仍可選中分模型，讓它依最新診斷修正，不是強制升高分。

🔵 **「公開驗收」是用事先說明的規則檢查成果，不是 CloudyFan 預先知道所有問題的正確答案。** 模型自信、排行榜高分，都不能代替這個檢查。隱藏答案、隱藏判分及其他組的答案，不得拿來選模或要求修正。

新規則不套回舊實驗；已凍結的任務保留原規則，也不重新發送已付費請求。

## 「完成」分成三件事

| 說法 | 白話意思 | 能證明到哪裡 |
|---|---|---|
| **實作完成** | 這個範圍的程式與接入方式已寫好。 | 不表示所有選配功能都做好，也不表示已在正式環境用過。 |
| **離線驗證完成** | 指定版本通過模擬服務、合成資料或固定客戶端的測試。 | 只證明測到的範圍；不能直接推論真實模型、硬體或部署也成功。 |
| **正式資格待核定** | 還需要實際範圍的證據，以及負責人與審閱者的確認。 | 不等於程式沒寫，也不能只靠測試數、Git 提交或 Issue 結案改成合格。 |

正式狀態以 [release-gates.json](release-gates.json) 為準。目前十項都待核定，負責人與審閱者尚未指定，正式證據欄仍空白。[實作索引](implementation-spec1.md)與[驗證紀錄](verification.md)則保留已做過的工作。

`project-state` 的 `implementation_complete` 會檢查程式、工作計畫與驗證紀錄是否一致；它不是正式放行證明。`production_qualified` 必須依正式核定記錄判斷，不能從某個模型池的 `production_ready` 或一張測試報告直接推定。本頁只解釋狀態，不更改檢查程式或資料格式。

## 各項已做什麼、還缺什麼

### 檢查答案與修正（RG-01）

**已做：** SQL 驗收器、資源限制、可公開的錯誤說明、工程錯誤分類，以及保存答案後接續執行。另有可選用的公開 SQL 測試組。新路由允許 CloudyFan 最多修正兩次，對照模式仍一次；SQL 判分規則不變。

**已測：** [SQL 接入](sql-environment.md)、[Scout 指定環境](rg01-scout-target-20261019.md)的正常流程 8/8、七項隔離／資源／中斷檢查 7/7，以及[公開測試組的回歸](evidence/sql-public-suite-precommit-20261020.json)。後續路由變更須另有對應回歸紀錄。

**還缺：** 對預定使用範圍，證明驗收器能可靠辨認沒見過的錯誤答案。已修好 F32／F48 的已知漏判，不等於其他答案都能判對，也不能說「只差簽名」。目前維持凍結，不重審 S01～S08；相關功能改變時才補必要回歸。

**注意範圍：** SQLite 記憶體分配限制，不等於整個程序的 RAM 或所有作業系統隔離都已保證。Scout 的測試也只適用當時固定的環境。

### 確認模型版本與能力（RG-02）

**已做：** 高／中／低模型池、候選資格與到期檢查、排除不合格候選，以及通過資格和預算檢查後才執行的入口。每個設定都會綁定模型版本、推理強度、供應商、SQL 操作與可處理的輸入長度證據。

**已測：** [模型池操作](first-pool.md)、[來源與能力資料檢查](first-pool-source.md)、[原 POOL 批次的 19 項新增回歸及完整測試](evidence/first-pool-offline-20261020.json)。公開資料已查到模型目錄、可指定的強度、供應商端點及宣告容量；這些是文件觀察，不是真實回答能力。

**還缺：** 實際呼叫時的模型身分，以及獨立 SQL 測試結果。[新版資格規則](sql-model-qualification-v2.md)已準備固定 API 版本表、全新 50 題和判分工具，但尚無這批真實模型結果，所以候選包仍是 `blocked`（資料不足，不啟用）。更換證據後，不能沿用舊審閱結果。

這批模型資格考試仍限定每題最多兩次同模型作答，與 CloudyFan 路由最多三次作答分開。離線準備與既存答案判分工具已完成；後續已接上[資格執行器](sql-model-runner.md)，以模擬上游演練答案保存與續跑。真實派送仍缺授權、可驗證的費用保障與實際資格資料，不能因執行器完成就啟用模型池。

**適用範圍：** 每個實際使用的模型設定都要確認；使用量化版時也要記錄量化設定。開源 API 的測試只能確認該供應商的服務設定，不能證明看不到的底層權重永遠不變，也不能證明本地 Mac Studio 已合格。

### 確認評分來源與更新方式（RG-03）

**已做：** 評分來源接入、受控匯入、依原排行榜尺度分群，以及固定版本的評分資料。更新可先預覽，再一次完整切換並留下紀錄；首版可以人工更新，不必先做自動排程。

**已測：** [模型池更新與舊任務接續](first-pool.md)、[更新規則](score-update-operations.md)及[模型池生命週期測試](evidence/first-pool-offline-20261020.json)。[公開查核](first-pool-public-evidence-20261020.md)讀取同三個既定評分候選，每個都取得來源的 64/64 覆蓋；分數、來源版本與取得時間可追查。這不是我們自己做了三次 64 題模型實驗。舊 14 筆觀測及 LiveBench v1 的歷史連線紀錄保留。

**還缺：** 確認來源資料可如何使用、是否適用，以及由誰更新、多久檢查一次、誰負責審閱。目前沒有把新候選資料設成正式使用版本。[人工來源流程](score-source-manual-operations.md)已整理使用範圍、期限、更新及故障處理；實際人員與使用依據仍待確認。

🔵 **排行榜用來安排高／中／低分群，SQL 測試用來判斷指定 API 設定是否能做這類任務。** 兩者分開。榜單沒提供的評測日期保持未知，不用下載日期冒充；SQL 資格另記實測日期與效期。首版只需核定實際採用的來源，不必接完所有排行榜。

### 算清完整費用並防止超支（RG-04）

**已做：** 共享預算、執行前預留整條流程可能花的錢、核帳、費用未知時停止，以及逐候選列出缺少哪些費用保障。也已實作供應商費用接入、各費目最高金額計算、完整零費率證據及 429 失敗費用處理。

新版 CloudyFan 的完整預留涵蓋三個可能作答階段、最多兩次分類及各階段可呼叫的工具，並計入各階段允許的生成輪數；對照模式仍按兩個作答階段計算。實付只計真正發生的請求，提早通過就不計未發生的選模或作答。費用未知、身分不符或工程錯誤仍停止派送，不能為湊足三次而繞過。

**已測：** [完整費用元件規則](component-bounds.md)、[429 費用處理](rejection-fee-policy.md)，以及[五個模型角色、40 個費用檢查格與七種路徑的缺證表](first-pool-fee-gaps.md)。模型能力與費用保障分開檢查，前者合格不會自動放行後者。

**還缺：** 真實供應商是否能保證最高收費，並涵蓋分類、初答、每次可能的修正，以及失敗、取消、供應商內部重試和已送出但還沒結算的請求。還要確認何時費用才算最終確定。

這些保證可以來自可強制的累計用量上限與有效費率，或該費目的完整零費率承諾。**事後帳單能對上，不等於事前一定不超支；價目表標零，也不等於所有失敗路徑都免費。** 所有受控模型與工具執行都需處理此項。

### 誰能使用、資料留多久（RG-05）

**已做及離線測試：** Token 身分、使用權限、金鑰輪替／撤銷、帳號停用、資料到期、停用舊資料及受控清除；見[身分管理](identity.md)、[資料保留](retention.md)及 HTTP／Ollama／Queue 回歸。

**還缺：** 實際環境的帳號、加密連線（TLS）、憑證保管、資料與備份存取權限，以及保留政策。啟用 HTTP／Ollama／Queue 等入口前需要確認；只把 Core.run 嵌入程式時，另行確認哪些要求適用。首版不強迫先加入 OIDC／SSO。

### 確認資料沒有送出本地（G-01）

**已做及離線測試：** 回答、分類與工具執行前，都檢查允許在哪裡執行；見[執行位置規則](execution-policy.md)及[本地文字接入](local-backend.md)。模擬測試涵蓋外送與拒絕路徑。

**還缺：** 在實際引擎、代理、工具與驗收器環境下，量測是否有對外連線，也要涵蓋失敗、分類及修正。

**只有要承諾全程本地（`local_only`）時，才需要這項資格。** 本地網址或本地首答，不能證明整條流程沒有外送；若後續會用雲端 Jev，就不能宣稱全程本地。不能為了通過檢查而暗中放寬規則。

### 確認指定客戶端可以接上（G-02）

**已做及離線測試：** 官方 Python 同步 `ollama==0.6.3`，限定單輪、非串流文字及 `text-v2` 協定。已測認證、錯誤處理、連線中斷後不重送，以及拒絕不支援功能；模型上游用模擬服務，見[SDK 接入紀錄](ollama-sdk.md)。同一任務的 GET 擴充可讀取狀態、結果、成本及路由紀錄，須由標準 HTTP 客戶端查詢，不是 SDK 內建方法，也不會自行向供應商核帳。未映射端點在正式身分檢查下以 401 拒絕，不宣稱都有端點專屬錯誤說明。

**還缺：** 指定審閱者確認這個精確版本與支援範圍。若要宣稱已在某個真實部署連線成功，還要補該環境的 TCP／TLS／代理證據。可先審閱既有紀錄，不必花模型費；不用先補 Async、JS 或其他產品客戶端。

**G-02 是「客戶端能不能接上」；RG-02 才是「模型版本與能力是否合格」。兩者不同。**

### 多人使用時的排隊與恢復（G-03）

**已做及離線測試：** QueueHTTPApp、排隊容量、使用配額、身分隔離、取消、重啟與受控背景執行；[排程測試](bounded-scheduler.md)涵蓋合成負載、同時操作、未知費用和中斷。

**還缺：** 先訂可接受的使用量、並行數、時限與延遲，再測實際等待、完整耗時、隔離及人工恢復。未知費用與預留金額不能在恢復時消失。需要排隊限制的請求都走 QueueHTTPApp，不能另開同步入口繞過限制。

提供多人排隊服務前才需要這項資格。`production_slo_validated` 仍為 false；首版可先採安全的人工恢復，不必先做自動事故恢復。

### 確認本地模型在指定硬體跑得動（RG-06）

**已做及離線測試：** 本地文字接入，以及記錄載入、切換、首個 token 等待時間（TTFT）和資源使用的框架。[現有測試](local-benchmark.md)使用模擬時鐘，涵蓋成功、記憶體不足與中斷，沒有測真實硬體。

**還缺：** 固定模型權重與校驗碼、量化、引擎版本、硬體、作業系統和 RAM，實測載入、回答、公開驗收、記憶體不足、中斷及指定工作量下的穩定性。模型回答能力仍由 RG-02 確認。

真正使用或宣稱支援本地硬體時才需要。Mac Studio 128G 仍是候選配置；透過 API 使用開源模型不等於本地硬體合格。若要宣稱切換、並行、TTFT 或功耗表現，需另有對應量測。

### 能否對外說「品質不變、比較省、比較快」（RG-07）

**已做：** 實驗前檢查、凍結規則、四組流程與結果綁定、相同題目的配對報告，以及完整費用和未知項保存。

## 正式狀態檔與檢查工具（維護者參考）

[release-gates.json](release-gates.json) 是正式狀態與責任人的唯一記錄來源。本頁解釋其要求，不用歷史測試數或 Issue 結案去改資格。離線執行：

```sh
.venv/bin/python scripts/release_gates.py
```

- **退出碼 0**：記錄格式與引用檔案有效。若仍有待核定項，輸出仍是 `production_ready: false`。
- **退出碼 1**：索引有錯、缺必要資料或證據過期。

這個工具不連網、不叫模型，也不部署。它只能檢查格式與檔案完整性，**不能證明證據是真的、簽核人就是本人、授權有效或測試適用**。即使輸出 true，也不自動授權付費、存取或啟動服務。

### 狀態與欄位規則

Schema v1 頂層只有 `schema_version: 1`、`scope: {id, description}` 和 `gates`。G-01～G-03、RG-01～RG-07 必須各出現一次。`scope` 要說明確切任務、模型、客戶端與環境，並由核定者確認；目前只是預定範圍，不是已批准的發布範圍。

每項只有 `id`、`status`、`scope_id`、`owner`、`reviewer`、`rationale`、`evidence`：

| status | 欄位要求 |
|---|---|
| `pending`（待核定） | 可指定 owner／reviewer，未指定填 null；evidence 是空陣列、rationale 為 null。失敗、未知與候選資料留在歷史紀錄。 |
| `qualified`（已合格） | 必須指定 owner／reviewer，至少一筆有效的 `real` 證據；rationale 為 null。模擬資料、Issue 結案或一般測試通過不能冒充真實資格證據。 |
| `not_applicable`（不適用） | 不刪除該項；須指定 owner／reviewer、寫清適用範圍與理由，並附有效的 `scope_decision` 核定紀錄。 |

每筆 evidence 只有 `kind`、`method`、`result`、`scope_id`、`path`、`sha256`、`observed_at`、`expires_at`、`authorization_ref`：

- 已合格：`kind: real`、`result: passed`，method 為 `observed_execution` 或 `manual_review`。
- 不適用：`kind: scope_decision`、`result: approved`、`method: manual_review`。
- scope_id 必須與該項及頂層 scope.id 一致。去敏核定文件須寫明執行者、核定者及精確範圍，不能只寫「通過」。
- path 必須是本 repo 內相對路徑，不能含 `..`、絕對路徑或經符號連結指向外部。sha256 是檔案的 64 位小寫十六進位校驗碼。
- 日期含時區，符合 `observed_at <= now < expires_at`。authorization_ref 只引用既有授權，填文字不能創造新授權。

Python API `validate_gates(data, root, *, now=None)` 回傳錯誤列表，不改輸入或檔案；測試可注入含時區的 now。對同一份資料、同一 root、有效當下時間檢查無誤後，才呼叫 `production_ready(data)`。全部項目已合格或經核定不適用，結果才是 true。

檔案校驗碼只證明內容有沒有改，不證明做過實測；姓名欄位也不是簽章。把模擬資料謊稱真實資料仍可能騙過格式檢查，所以內容審閱不能由這個工具取代，也不能把它當成付費、安全存取或部署的授權機制。
