## 數值輸入域另需釐清

共同 prompt 的 `amounts ... and sums fit signed int64` 沒有明定只看**最終和**，或也限制
**所有可能的中間累加**。同一多重集合：

- `[9223372036854775807, 1, -1]` 的最終數學和可表示為 int64，但本機參考 SQL
  先加前兩值會溢位；v2 正確分類為 `SQL_VALIDATION_ENVIRONMENT`，不是模型答錯或成功。
- 換成 `[9223372036854775807, -1, 1]`，本機參考 SQL 可回傳該最大 int64 值。

這是新數值邊界探測，不是既有樣本失敗；也不擅自認定哪一種讀法是原意。
S01／S03 的整數 SUM、S07 的逐列 SUM 在宣告數值域前都須處理這個界線。
可以由使用者定義實際金額／筆數上界，或明確要求所有相關中間結果可表示；若要涵蓋
更大的數學整數域，必須另外設計驗收方式，不能只改文案宣稱已有支援。

## 不應誤判為錯誤的等價查詢

S07 的 `(day,id)` 在各 customer 內唯一，因 order ID 唯一且非 NULL。在相同完整排序鍵下，
`RANGE ... CURRENT ROW` 與 `ROWS ... CURRENT ROW` 沒有不同的 peers，結果可以等價。
本輪正向控制確認該等價寫法能過原樣本；不應要求模型只照抄 reference 的字面形式。
真正確認的問題是省略 ID tie-break、改變 NULL 日期位置或漏掉合法群，而非任何 RANGE 都錯。

## 仍需使用者確認的事項

1. **首版評審範圍與主張**：是否採用這八類有限 SQLite 唯讀任務作候選領域？確認的應是
   哪些輸入／資料與結果用途；不能把它解讀成 CloudyFan 全部任務或任意 SQL 的資格。
2. **業務語義是否符合用途**：空／全 NULL 合計為 NULL；S06 全 NULL 群仍回傳最小 ID；
   S07 NULL 日期最先、NULL 金額貢獻零；S08 大小寫敏感且保留空字串。若要不同業務規則，
   以新版本處理。原已寫明的 0／負 ID 與非 NULL 無主引用，本輪不自行縮小範圍以求通過。
3. **實際數值域**：最終值與中間運算的上界如何界定？金額是否以整數最小單位表達？
   尚未確認時維持未核定，不自行填入金額／筆數假設。
4. **正式責任與環境**：由誰具名核定語義／覆蓋、何人審閱，及精確目標執行環境。
   本機嚴格地址空間模式不可用、SQLite allocator 非完整 RAM／OS sandbox 的限制不變。
