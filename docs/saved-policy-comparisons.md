# Saved original-policy comparisons — Issue42 candidate

The operator can explicitly create an immutable report through `POST /monitor/comparisons`, supplying only a registered policy version and 1–20 distinct `{client, run_id}` identities. The same operator/host/origin guard protects the catalog and report GET. Customer tokens cannot see the global reports. No browser-provided path, URL, receipt, code or answer is accepted.

A comparison ID is a separate `cmp-` namespace. Creation never calls TaskService execution, queue admission, a model/tool client, source refresh, Budget report/sync or billing reconciliation. The trusted host maps identities to original binding, identity, retention and contract authorities. A short-lived subprocess receives only explicit host paths and values; the pure Core comparator receives only the verified, bounded JSON decision DTO, with no paths, client, service, callback, prompt, answer or diagnostic prose.

The host loaders re-apply the original ordinary Core's four modes, frozen QCS direct/classified choices and both quality stages, and Backup initial/same-pool/two-stage quality continuations. They verify original generation/validation and classifier input/response bindings, including original parse failure, missing-distribution and tie fallbacks. The classifier follows the original strict JSON numeric grammar; accounting metadata keeps its separate money-string contract. Decimal representation bounds are checked before fixed-format expansion. A valid original probability outside those comparison bounds stays unknown, while bounded scientific/plain spellings compare by exact Decimal value. A content-derived configuration ID for an ordinary profile is an identity reference, not qualification. Original tiny fees accept bounded scientific notation and are displayed as equivalent plain decimals; saved economic money comparisons use exact bounded Decimal equality, not a tolerance.

Backup availability exhaustion uses separate checkpoint, attempt and saved-selection cursors. A verified empty same-pool decision must first reproduce `advance_quality_stage`; only its actual input SHA can become the next quality point's optional proof. The original availability stop remains unchanged, the transition consumes no generation, and the final public stop carries no exhaustion proof. Missing proof cannot authorize this reproduction. Every family stops after the first missing, inconsistent or different choice; a later actual answer is never borrowed to continue an uncertain reproduced path. Original actual paths and costs remain visible independently.

These are decisions from frozen admitted profiles and recorded gates. The loader does not requalify upstream whole-pool admission or financial authority, and never substitutes current health, quota, price or candidates. Backup historical Health snapshot membership and policy hashes are checked. The response-window adapter checks original adoption/dispatch/configuration/window identities, physical group scope and the complete related observation prefix up to the recorded revision. A referenced row must bind its original request/response and transport hashes, header grammar, reported time, constraint aggregation and safe reason. Dependency responses may come only from explicitly selected tasks, with each source's original principal, permission, contract and raw access period independently verified. A shared physical account can have a source from another explicitly selected client under those same checks.

The verified saved window predicate is an input to candidate ordering. The adapter does not recompute the window builder: its historical evaluation time was not persisted. In particular, recorded open revision1/2 does not heal an original Health exclusion, and unreferenced raw data is not reopened to invent a past clock. An authenticated original unknown gate is the original fail-closed exclusion; missing or inconsistent provenance makes the comparison unknown. Explicit controlled-source imports use a separate obligations protocol and remain unsupported by this response-reference adapter. Targeted window validation includes source-discovery isolation, selected cross-client authority, missing/corrupt evidence, revoked/expired sources and customer report isolation; it does not replace the original complete project gates.

Original actual paths, task state and authoritative original Budget fees remain separate from reproduced decisions. Pending or missing fees remain null/unknown, not zero. Remaining original Budget rows supply only the observed known sum; receipt amounts never repair missing ledger rows. An auxiliary event snapshot can be an earlier prefix, so an equal pair of empty sets does not establish complete fees. For a terminal task without configured tools, the existing safe complete trace must account for every generation-call identity and the classifier count before its retained account/event set can establish coverage. Missing rows then invalidate completeness while preserving the observed known sum. Unproven event kinds, incomplete traces or absent anchors leave completeness unknown. A never-dispatched zero additionally requires the original shared task lock, ready state, no reservation/events and no execution artifacts; a queue-created deadline alone is not execution. Customer usage fees come only from already-written customer ledger records. After original raw access expires, the loader uses safe retained history and account/event identities; it never opens the job, manifest, checkpoint or call payload. Comparison output does not renew access, change tariffs/modes/expiry, sign observations or adopt a policy. There are no alternative model outcomes, win rates or real-saving claims.

Private report files contain the fixed scope/time/versions/implementation hashes, safe frozen decision inputs and data-use limits, safe result, worker exit/PID/timing evidence, and final request/input/report hash seal. Implementation identity covers all three family/window adapters, original Core policy/routing/Decisions/usage/reasoning and capacity protocol definitions, and host metadata validators, plus Python/SQLite versions. Report GET validates the saved request/input/result relationships with their original limits and returns the saved result; it does not reread task/code evidence or recompute. Historical limits must retain the exact known v1 keys, positive integer types and the original finite schema ceilings. Later creation limits govern new requests and do not invalidate an old report or catalog entry. The capture uses one private generation per source DB within a fresh report and recorded original predicates; it is not an atomic transaction across all original stores or a cache shared across reports. Unqualified economic savings are not a public output; original policy reason codes are distinct from achieved model-cost savings.

Declared per-creation limits are 20 tasks, 256 source captures/projections, 4 MiB total source bytes, 1 MiB per original file, 12 candidates, 9 decision points, 256 KiB public result, and 250 ms pure policy computation. The isolated loader/compute child has a 2-second CPU and 5-second wall limit, is killed/reaped on timeout, and replaces the Python `socket` module's connection and DNS entry points. That is a tripwire, not a sandbox: safety rests on the worker holding no model, tool, source or accounting client. Its private TMPDIR, which holds the store copies, belongs to the parent and is removed even after a kill. The comparison never takes Core's exclusive task or retention locks; it re-reads the task's mutable files after loading and marks a changed task unknown. These are worker limits, not a whole HTTP/OS-I/O latency guarantee. Oversized or unavailable sources produce explicit unavailable/unknown results; overall source-budget exhaustion is incomplete. Source DB+WAL bytes count toward the source limits. Thus a larger original database may be ineligible for this bounded loader; it is not scanned without limit.

SQLite never opens a live original pathname after a separate pre-check. Main DB and optional WAL are captured through safe parent/leaf descriptors with NOFOLLOW/NONBLOCK, regular/nlink/size checks, and stable before/after identities for both. A rollback journal before or after capture rejects the read rather than making an uncommitted main file appear committed. SQLite opens only private temporary copies using ordinary committed-WAL semantics, readonly/query-only/timeout0, incrementally bounded row materialization and a VM-step bound. It never uses `immutable=1` to discard WAL or writes original SHM. Original task, retention and run locks are shared/nonblocking and never created, changed or held for execution. Advisory locks assume original cooperating writers; arbitrary privileged writers are outside that contract.

Current validation is targeted and offline only: real loopback main-service HTTP, original Store/identity/Core/Budget/scheduler and MockTransport, with nonloopback denied. Initial failed runs and test-setup mistakes are preserved separately. Headed desktop, original Core integration full, original Monitor full/build, final fixed-source review and independent acceptance remain pending until their actual receipts exist. No provider spend, push, deployment or evidence cleanup follows from this document.

## Registered candidate strategies — Issue43

A creation request may add one `candidate_strategy` from Core's `saved_candidate_strategy.STRATEGIES` (`qcs-direct-v1`, `qcs-classify-v1`); any other value, type or browser-built policy is rejected before a report exists. The catalogue lists only those names. Reports created without a strategy keep their original scope and result digest.

For each saved decision the worker passes the same verified value DTO to Core twice: the original reproduction and the registered strategy, within the same compute budget. A strategy only changes the QCS direct/classify judgement; every other step is reported as identical to the original. Classification reuses the original reply rules only when the original sent that same classification request. The first divergence stops evaluation (`requires_unsaved_alternative_answer` or `requires_unsaved_classifier_reply`); later steps are `not_observed`, never failures.

Missing exact classifier calibration, an unsaved classifier estimate and an over-limit classification flow are reported as `not_evaluable` or `not_adoptable`, distinct from an uneconomic classifier. Forecasts come from the original saved cost model and are labelled as forecasts: complete-flow interval, classifier fee estimate, conservative net saving and calibration state. They are separate from actual fees, customer charges and enforceable bounds. There are no alternative success rates, win rates, real savings or adoption; `adopted` is always false.

Validation is offline: Core unit tests, real loopback main-service HTTP with MockTransport for QCS direct/classified, second-stage quality rescue, Backup missing calibration and availability exhaustion, and a headed desktop run. The uneconomic-classifier case is covered by Core unit tests because no existing HTTP fixture produces it. No provider spend, push or deployment follows from this document.

## 相同輸入的已保存成果配對 — Issue44

建立比較時可加上 `pairing: "same-input-v1"`，這是目前唯一註冊的配對規則。規則與 `paired-saved-outcomes-v1` 指標在讀取任何原任務之前就寫入請求，所以不能在看到成果後再挑題或剔除。私有配對鍵由原類別、註冊契約版本，以及原請求 prompt 的雜湊組成；它只存在私有的凍結輸入中，不出現在公開報告。原文存取到期後也不會再計算，這類任務會連同原因列為「排除」。契約 ID 不納入配對鍵，因為它代表的是各模式自己的執行器。

每個成員只提供自己保存的流程：最終任務狀態、首答公開驗收狀態、權威完整費用與條件。以下情況整組不可比：只有一種策略、同一策略有多筆流程、候選池或契約版本不同或未知、有流程尚未完成。保存資料沒有記錄快取條件，所以所有配對都放在同一個明示的「未記錄」分層。只有每個成員都通過相同公開驗收、且完整費用都已知的組，才報費用差；品質不同、沒有已驗收工作或費用未明的組照樣列出，但不報費用差。各策略的合計把已知金額與費用未明流程數分開；沒有已驗收工作或有費用未明時，「每件已驗收工作的完整費用」標為未定義，不填零。「觀察到救回」只用在同一流程首答公開驗收未通過、最終通過的情況，不推論 Jev 的因果效益。

報告列出選定、可配對鍵、排除、已配對、未配對、品質相同、品質不同、無已驗收、費用未明、不可比等數量。不報勝率、替代成果或真實節省，不採用任何策略；計算配對不重新驗收，也不呼叫模型、工具、來源或核帳。驗證範圍為離線：純函式單元測試，以及真實本機 loopback 主服務 HTTP 搭配 MockTransport，涵蓋品質相同、品質較差且觀察到救回、輸入不同與同模式重複、到期排除、未註冊規則拒絕，另有 headed 桌機驗收。

## 局部失敗、建立失敗與重跑 — Issue45

- 每個查詢的列數上限（例如原預算事件最多 64 列）只讓「那一件」任務標為 `original_rows_over_limit` 未知，不再把整份報告標為未完整，也不影響同報告後面的任務。總位元組、檔案數、計算時間與工作程序時間上限仍是整份報告的上限，超過時照舊標「計算未完整」。
- catalog 依名稱排序後最多掃描 1,000 份請求，只回傳最新 100 份；超過時 `reports_truncated` 為 true。一份已封存報告無法核對時，只把那一份標為 `unavailable`，其他報告照常列出；單獨讀它仍回 503 `comparison_evidence_unavailable`，不重新計算。
- 請求已寫入、但封存前失敗（例如來源內容無法取得或輸出超限）時，另存 `.failed.json` 記錄失敗原因與時間。catalog 標 `failed`，讀取時回 409 `comparison_creation_failed`，與仍在處理中的 `pending` 分開；之後的比較不會覆寫這筆失敗。
- 建立時可加 `rerun_of`，指向一份可核對的既有報告：新報告有新的識別，範圍（任務、候選策略、配對規則）必須與原報告完全相同，報告內記錄 `rerun_of`；原報告不變。原報告無法核對時回 409，範圍不同時回 422。
- 驗證範圍為離線：真實本機 loopback 主服務 HTTP 搭配 MockTransport，涵蓋單件超限、損壞報告、建立失敗、重跑引用；另有 headed 桌機驗收。

## 相同原始結構輸入，依內容準備分層 — Issue53

- 新增配對規則 `same-original-input-v1`。它和 `same-input-v1` 一樣在讀取成果前寫入請求；配對鍵是原類別、契約版本、原 prompt 雜湊與整份參考區塊。
- 每個成員的策略是「模式｜準備版本｜結果」，例如 `open_source_first|extractive-v1|prepared`、`fixed_high|extractive-v1|no_reduction`；沒有參考區塊時是 `模式|none`。所以同一份原始輸入的整塊選取、沒有省略與逾時回退，會分在不同策略。
- 成員只附安全的準備資訊：版本、結果、原始與送出長度、送出內容是否與完整原文不同（`sent_input_differs`）、是否為合成接線資格。不含原文、區塊識別或內容。送出內容不同時，報告與桌機明示「不是相同派送輸入」。
- 費用差與品質門檻沿用 #44：只有全員通過相同公開驗收、且完整費用已知的組才報差。本機擷取沒有額外模型費，但準備時間與主機營運成本沒有量測，不假設為零，也不按 token 差補扣或退款。不報勝率、一般語意等價或真實節省，也不自動採用壓縮政策。
- 原任務載入器接受含參考區塊的新格式：
  - 綁定指紋與 Monitor 接收時一致，包含 `context`。
  - 執行 manifest 的 prompt 以 `task_prompt(job)` 核對；凍結準備損壞時視為不可驗證。
  - `context_policy` 是 TaskService 接收層的註冊欄位，不在 Core 執行 manifest 的比對範圍。這一項原本會讓所有含參考區塊的任務載入失敗，已在本張修正。
- `same-input-v1` 的配對鍵在有參考區塊時也納入整份區塊；沒有區塊的舊任務，鍵值不變。
- 驗證範圍為離線：真實 loopback 主服務 HTTP 搭配 MockTransport，涵蓋整塊選取與完整原文配對並報差、品質不同不報差、區塊不同不配對，以及既有六組比較回歸 116 項；另有 headed 桌機驗收。
